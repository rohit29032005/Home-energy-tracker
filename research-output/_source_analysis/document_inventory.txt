P006 style='Normal' drawing=False: Abstract - Residential energy platforms require a traceable route from meter-like telemetry to controlled feedback. This study implements a local 17-service Docker composition combining Wokwi-compatible ESP32 telemetry, API-gateway admission control, Apache Kafka, InfluxDB, MySQL, deterministic insights, and duplicate-aware alert delivery. User-facing routes apply Keycloak JWT, role, and ownership checks, while simulated-device ingestion uses a device token. A Random Forest anomaly model is selected by validation F1 from the supplied CSV and deployed as a fixed FastAPI artifact; its held-out precision, recall, F1, ROC-AUC, and PR-AUC are 0.880952, 0.925000, 0.902439, 0.997430, and 0.948532, respectively. Controlled local checks recorded a 1.50 kWh analytics case, a 1.00 kWh threshold-alert case, eight expected security statuses, duplicate suppression within 15 min, eight active Prometheus targets, and 450/450 accepted k6 ingestion requests. The results demonstrate implementation-level integration and bounded local evidence, not physical-meter accuracy, field-model generalisation, production security, or production-scale resilience.
P007 style='Normal' drawing=False: Keywords - Home Energy Tracker, Internet of Things, microservices, Apache Kafka, anomaly detection, Keycloak, alert deduplication, Wokwi simulation.
P008 style='Normal' drawing=False: I. INTRODUCTION
P009 style='Normal' drawing=False: Residential electricity bills provide limited visibility into when energy is consumed, which registered device contributes most, or when a configured threshold is exceeded. A practical Home Energy Management System therefore needs an auditable path from telemetry to stored records, interpretable outputs, and controlled notification. Recent IoT systems demonstrate affordable sensing and remote visualisation, whereas other studies focus on energy analytics or anomaly detection [3]-[6], [13], [16], [18]-[21], [23].
P010 style='Normal' drawing=False: This work addresses the integration of a local, event-driven energy platform rather than the accuracy of a physical meter. The deployed composition separates user and device metadata, ingestion, usage, insight, alert, API gateway, and ML inference functions, and includes Kafka, InfluxDB, MySQL, Mailpit, Keycloak, Prometheus, Grafana, and a frontend. Wokwi supplies timestamped synthetic JSON payloads to the same HTTP ingestion contract intended for a future meter; Kafka decouples request acceptance from downstream persistence and analysis.
P011 style='Normal' drawing=False: The study makes three bounded contributions: it implements a 17-service local Docker path from simulated telemetry to time-series storage and access-controlled APIs; it trains and deploys a fixed anomaly-inference artifact while retaining deterministic bill, ranking, standby, and threshold functions; and it records controlled local evidence for end-to-end behavior, gateway security, alert deduplication, observability, ingress load, and selected outage conditions. The scope excludes calibrated sensing, utility-bill validation, physical-field generalisation, production penetration testing, and production-scale resilience claims.
P012 style='Normal' drawing=False: II. RELATED WORK AND RESEARCH GAP
P013 style='Normal' drawing=False: A. Existing Approaches
P014 style='Normal' drawing=False: The literature represented in the source paper spans three complementary directions. Low-cost IoT systems use ESP32-class controllers and energy sensors to expose consumption or power-quality information [3]-[6], [13], [16], [18]-[21], [23]. Their measurement evidence cannot be transferred to the Wokwi-generated values used here. A second direction uses machine-learning or statistical methods for appliance classification, anomaly detection, and behavioural analysis [1], [7]-[11], [15], [22]. The present system evaluates a binary classifier only on its supplied labelled CSV and does not equate those results with real-household anomaly performance.
P015 style='Normal' drawing=False: A third direction considers microservices, cloud organisation, or distributed control for energy-management systems [2], [12], [14], [17], [24]. These works motivate service separation, event processing, and maintainability, while leaving a practical need for a traceable prototype that links a telemetry contract, access-controlled API boundary, event broker, time-series persistence, deterministic insights, anomaly inference, and duplicate-aware notification. The present work adopts this integration focus without claiming equivalence to the scale or fault tolerance targeted by prior architectural research.
P016 style='Normal' drawing=False: B. Research Gap and Contribution
P017 style='Normal' drawing=False: The research gap is limited implementation-level linkage between residential telemetry, event-driven services, controlled access, historical storage, transparent analytics, anomaly inference, and alert delivery with explicit verification boundaries. The proposed system addresses that gap through Wokwi-compatible telemetry, gateway admission control, Spring Boot microservices, Kafka, InfluxDB, MySQL, a deployed Random Forest artifact, deterministic insight functions, and Mailpit-backed alerting with a configured deduplication window. Remaining gaps include calibrated sensing, documented dataset provenance, per-household contextual labels, field validation, production-grade security assessment, and distributed resilience evaluation.
P018 style='Normal' drawing=False: III. PROPOSED SYSTEM AND METHODOLOGY
P019 style='Normal' drawing=False: A. Architecture and Telemetry Path
P020 style='Normal' drawing=False: The runtime input contains deviceId, energyConsumed, and timestamp. Wokwi firmware emits this JSON payload at an approximately 8 s interval; Eco, Heavy, and Alert Test modes generate controlled values for integration demonstration and are not calibrated physical measurements. User-facing requests enter through the API Gateway with Keycloak JWT, realm-role, and ownership checks, while Wokwi-compatible ingestion uses an X-Device-Token. The Ingestion Service validates accepted payloads and publishes energy-usage events to Kafka.
P021 style='Normal' drawing=False: The Usage Service consumes energy-usage events, writes time-stamped energy_usage points to InfluxDB, and derives selected-window aggregates. User and Device Services maintain household, appliance, and alert-setting metadata in MySQL. In parallel, an ML worker calls a FastAPI service that loads a fixed Random Forest artifact and publishes anomaly-results. Threshold and anomaly paths reach the Alert Service, which persists notifications and uses a configured 15-min deduplication window. Prometheus and Grafana provide service-level target and metric observation.

P026 style='Normal' drawing=False: B. Deterministic Insight and Alert Methods
P027 style='Normal' drawing=False: The Insight Service derives deterministic outputs from aggregated usage. It computes a daily rate and a 30-day energy projection from total energy E over D selected days. The configured local tariff uses a fixed 10.00 charge and slab rates of 0.12 per kWh for 0-100 kWh, 0.18 per kWh for 100-300 kWh, and 0.25 per kWh above 300 kWh. Device ranking uses each device total divided by the household total, and the standby estimate remains 20% of average load. These are demonstration rules, not a utility tariff or an appliance-level standby measurement.
P029 style='Normal' drawing=False: The anomaly branch uses the supplied smart_meter_data.csv with 5,000 records and seven columns, including Electricity_Consumed, weather/context fields, Avg_Past_Consumption, and Anomaly_Label (4,750 Normal and 250 Abnormal). Records are stably ordered by timestamp; Hour, DayOfWeek, and ConsumptionDeviation = Electricity_Consumed - Avg_Past_Consumption are derived. A chronological 3,500/750/750 train/validation/test split compares a balanced logistic-regression pipeline with a 300-tree balanced-subsample Random Forest. The Random Forest threshold 0.31 is selected by validation F1 and its saved artifact is loaded at FastAPI startup; missing optional context is median-imputed. The dataset source, licence, and label-generation provenance are not documented.
P031 style='Normal' drawing=False: For threshold alerting, a scheduler evaluates the preceding one-hour household sum every 10 s. When alerting is enabled and the sum exceeds the user-defined threshold, an energy-alerts event is published. The Alert Service consumes threshold and ML anomaly paths, persists alerts in MySQL, and attempts SMTP delivery with Mailpit as the local demonstration inbox. Its deduplication key is userId:deviceId-or-HOUSEHOLD:alertType; matching keys are suppressed during the configured 15-min window. The ML worker includes a bounded default of three attempts and an anomaly-processing-failures topic as implemented handling, not as a separately evaluated recovery guarantee.

P043 style='Normal' drawing=False: IV. IMPLEMENTATION AND FUNCTIONAL VERIFICATION
P044 style='Normal' drawing=False: A. Implementation Environment
P045 style='Normal' drawing=False: The system was exercised as a local, single-host Docker deployment on Windows 11 Home Single Language (10.0.26300) with eight logical processors and 7.74 GiB RAM. The compose configuration defines 17 services covering relational, event, time-series, e-mail, identity, application, frontend, and observability functions. The environment supports controlled implementation and verification; it is not a replicated cloud or production deployment.

P064 style='Normal' drawing=False: B. Interpretation and Evidence Boundaries
P065 style='Normal' drawing=False: On the supplied held-out CSV, the Random Forest achieved substantially stronger precision, F1, ROC-AUC, and PR-AUC than the logistic-regression baseline. This supports the selection of the saved Random Forest artifact for this dataset and split, but it does not validate field anomaly detection. The E2E analytics and alert observations demonstrate a traceable local integration path from synthetic REST input to stored usage, deterministic outputs, and a captured notification; they do not establish physical-meter accuracy or utility-bill agreement.
P066 style='Normal' drawing=False: The eight expected gateway statuses provide functional evidence for the tested authentication, authorization, ownership, administrator, device-token, and expiry scenarios. The duplicate-event experiment demonstrates one controlled suppression within the 15-min window. The Prometheus snapshot shows eight active targets up, and the k6 result measures only local gateway ingestion under the stated workload. The two outage checks show that ingress returned HTTP 201 while Mailpit or ML inference was stopped and that manual restart recovered the container; they do not demonstrate automatic recovery, replay, notification delivery, or general fault tolerance.
P067 style='Normal' drawing=False: The data and runtime boundaries remain material. The CSV has no documented source, licence, label provenance, household/device identifier, or provenance for Avg_Past_Consumption. Its Electricity_Consumed values are in an undocumented 0-1 range, whereas Wokwi modes send direct values in approximately the 1-40 range; optional Wokwi context is median-imputed and no range-validation or calibration experiment is reported. No runtime ML latency is reported because the observed inference-latency counter had zero samples.
P068 style='Normal' drawing=False: VI. LIMITATIONS AND FUTURE WORK
P069 style='Normal' drawing=False: The principal limitations are synthetic, non-calibrated Wokwi telemetry; the anonymous dataset and missing provenance; the training-to-Wokwi unit/range mismatch; and the absence of physical-meter, utility-bill, and external-field validation. The evaluation uses one local Docker host with a bounded ingress test, no distributed tracing or Kafka-lag study, and only selected manually recovered service-outage checks. Keycloak and gateway controls were functionally checked in eight HTTP cases, but no TLS/cloud deployment or penetration assessment was performed. The deterministic standby estimate remains a 20% average-load heuristic.
P070 style='Normal' drawing=False: Future work should collect consented, documented, calibrated interval-meter data with per-device and household context; establish label and feature provenance; and add range or out-of-distribution checks before model deployment. It should repeat end-to-end and load measurements over longer workloads, add tracing and Kafka-lag instrumentation, and perform automated fault, retry, failure-topic, replay, and recovery experiments. Production hardening should address TLS, secret rotation, device provisioning, and an independent security assessment before any real-world deployment claim.
P071 style='Normal' drawing=False: VII. CONCLUSION
P072 style='Normal' drawing=False: This paper presents a microservices-based Home Energy Tracker updated from an integration baseline to a locally evaluated event-driven system with gateway access controls, Kafka-mediated processing, InfluxDB and MySQL persistence, deterministic insights, a deployed Random Forest inference artifact, alert deduplication, and Prometheus/Grafana observation. Controlled evidence includes the supplied CSV model assessment, synthetic E2E analytics and alert checks, eight gateway-security cases, duplicate suppression, an eight-target snapshot, local k6 ingress measurement, and two limited outage-availability observations. The work demonstrates implementation-level integration and bounded local verification; it does not establish meter accuracy, externally generalisable anomaly detection, production-scale performance, comprehensive resilience, or production security.
